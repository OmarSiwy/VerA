# Peak memory of the processes VerA owns

Measured 2026-10-01 on branch `perf/memory`. The commits were written on `45022040` and rebased onto `a0cc077d`; every after-number was re-measured on the rebased tree, Zig 0.16.0,
Intel i9-14900HX, 31 GiB. The question: the "16.4 GB" seen on a strict suite
run, and whether every process VerA's own code runs can stay under 100 MB on
the worst input in the corpus.

Measures A/B/C/D: none moved. Every compiler change here is byte-identical
(goldens of all 2168 `.va` fixtures and of the 104 ARPice models; transcripts
and device text of all 1049 `.v` fixtures).

## What "16.4 GB" was

A cgroup `memory.peak` of the whole strict suite: page cache from writing
~17 GB of testbench artifacts into `.zig-cache/vera-suite/` (1403 testbench
executables plus objects) and the child `zig build-exe` processes, which VerA
controls only through the fan-out. No VerA process came near it; see the
suite table below for what each process class actually reaches.

## Method

* **Peak RSS** is `ru_maxrss` of the process from `wait4`, taken by a 20-line
  static C wrapper (`peak`). Python's `resource` module was tried first and
  reads 13.5 MB for `/bin/true`: the forked interpreter's image is charged to
  the child before `exec`. Every number below comes from the C wrapper,
  whose own floor is 3.9 MB (`/bin/true`).
* **Where the bytes go**: phase probes (`VmRSS`/`VmHWM` and arena capacity at
  each pipeline stage boundary) and a counting `Allocator` wrapper keyed by
  return address, symbolised with `addr2line`. Both were temporary patches,
  not committed.
* **CPU** is the minimum user+sys over 15 runs (the host was loaded by other
  agents' builds throughout, so wall time is not quoted).
* Suite processes: a sampler reading every PID of the gate's cgroup every
  0.25 s (`VmRSS`, `memory.stat anon`).

## The changes, in commit order

1. `524d8840` **perf(ssa): chunked (place, block) map.** Braun's SSA reads
   memoize their answer in every block they walk, so on a compact model the
   (place, block) matrix is written wherever a place is live: psp103 is 2070
   places x 4234 blocks, 1.69 M cells written (19 %), 65 % of them in
   single-predecessor blocks. The matrix was one dense mapping whose untouched
   pages stayed free, but growing its block axis copied every row whole, zeros
   included, while the old mapping was still live. That copy was psp103's
   peak: 129 MB at lowering against 41 MB at the end of codegen. Now: a dense
   directory of 64-cell chunks (256 B, against a 4 KiB page) allocated on
   first write, with chunk 0 the shared all-absent chunk, so a read stays a
   branch-free two-load path (the sentinel idiom from `/branchless`).
   psp103 129 → 43 MB, hisimhv 141 → 94 MB, psp103_nqs 100 → 53 MB.

2. `f836ae3b` **perf(root): BigArena.** The compile ran on one
   `ArenaAllocator`, which can grow only its latest allocation in place: every
   doubling table (MIR rows, `extra`, the AST stores, codegen buffers) left its
   outgrown buffer resident until the compile ended. The ZvsRust study's E10
   found the same thing from the other side (an arena reached the reused
   workspace's allocation count at 7x the peak). `lib/big_arena.zig` keeps
   the arena's lifetime (one `deinit` frees everything) but passes blocks of
   64 KiB and up to the gpa, where `smp_allocator` grows them with `mremap`
   (no copy) and unmaps a dropped one at once. A resize across the 64 KiB line
   is refused, so a block never changes sides. hisimhv 94 → 58 MB, psp103
   43 → 31 MB, and CPU fell with the page faults (hisimhv 411 → 295 ms).

3. `b22f5a70` **perf(cli): the `.v` elaboration arena is a BigArena.**
   400 → 164 MB on the 524288-net design.

4. `e46a2c2b` **perf(analysis): fold columns as kind + bits arrays.** Codegen
   keeps two `[]?Const` per MIR Value for the whole emit; a `?Const` is 24 B,
   all of it for the string arm's slice. `FoldColumn` is a kind byte plus the
   int/real bits (or a string's index): 9 B. Analysis.build on hisimhv
   11.7 → 6.1 MB.

5. `2af7074a` **perf(ssa): the builder's own tables leave the compile
   arena.** Predecessor, phi-user and per-block tables are lowering scratch;
   they now live beside the map and are freed when lowering returns, instead
   of riding the compile arena into codegen. RSS after lowering 29.6 → 28.9 MB
   (hisimhv).

6. `afed0fc1` **perf(sim): hot/cold Net rows and flat per-net runs.** An
   unpacked net array is one `Net` per element (IEEE 1364 §4.9.1). `Net` was
   184 B; the delay, inertial transition, trireg decay and pass-switch list
   are now a `NetCold` row only a delayed net, a decaying trireg or a switch
   terminal has, leaving 72 B. Each net's drivers and switches are runs of
   one flat array (a counting sort, the CSR shape `buildFanout` already used)
   instead of a 24 B list header per net, two such tables having been alive
   at once; the per-slot event-term list is a pointer made on the first wait;
   spent cursors are freed where they die. 164 → 107 → 88 MB.

7. `1e6d8956` **perf(sim): `net_of` is one u32 a slot.** Which net a slot is
   was an `AutoHashMap(u32, u32)`; with nets the common slot, the map paid
   two entries' worth per net plus its rehash copies, and a probe per lookup.
   `SlotNets` keeps `get`/`contains`/`put` over a dense column. 88 → 80 MB,
   CPU 115 → 87 ms.

## Floor: why not 10 %

* **~5 MB** is the process itself: binary pages, libc, and the annex D/E
  prelude every compile lexes. The median fixture is 5.5-5.9 MB, of which the
  compile is a few hundred KB; the +0.4 MB median shift after this branch is
  binary layout: a rebuild that changed nothing on the `.va` path (the
  digital-arena commit) moved the same input by -0.4 MB.
* **The whole-module pipeline keeps every stage resident at the end.**
  Codegen reads MIR, `Lowered` and `Analysis` until the last unit is written,
  and the AST stays alive because `Lowered.file` points into it (the prover
  and the VPI host read it). Freeing the AST before codegen would save ~6 MB
  on hisimhv but needs a separate front-end arena, and MIR string slices
  borrow from the AST interner and the preprocessed text, so that is a
  lifetime audit, not a one-line drop.
* **The device text is 4.2 MB** and is built whole: the orchestrator cuts it
  into per-unit files by offset.
* Below ~40 MB on hisimhv needs streaming codegen (plan and emit one unit,
  drop its tables) and a front end that hands lowering a smaller tree.
* The digital interpreter is ~145 B a net after this branch (72 B `Net`,
  24 B `Literal`, two 16 B plane blocks, a `net_of` cell, a strength row). A 524288-element
  wire array is still one net per element; storing an array net as one
  row with a bit-plane would be the next order of magnitude, and is a change
  to how `§4.9.1` arrays are executed, not a layout tweak.

## Audit, not applied

* **Held-array copies in the generated device** (coupled_ltra, txl). A §5.10
  held array is copy-on-write in the core: `p<id>` reads the `Instance`
  field, the first store copies it into a local `a<id>`. `updateState` then
  calls `core__state`, which returns every held array by value, and copies
  each into `inst`. For coupled_ltra (2048 + 4 x 4096 doubles) that is
  147 KB of locals plus a 147 KB result struct, ~295 KB of stack in
  `updateState`, and three 147 KB `memcpy`s per accepted step. It is a
  stack-depth and time cost, not RSS (a stack page is touched once). The
  zero-copy shape: give the `__state` slice a `*Instance`, let a held array
  whose final version is its own storage be written in place (the codegen
  already guarantees one live version per storage, which is what makes
  copy-on-write sound), and drop that field from the result and from the
  store-back in `updateState`. Device text changes, so it is a minor version
  with regenerated size goldens; not done here.
* **`--emit-exe` keeps the compile alive while `zig build-exe` runs.** ~50 MB
  at worst against a ~1 GB child; not worth the restructuring.
* **Per-element allocations in `mintNet`**: three small arena blocks per net
  (two bit-plane pairs and the strength row). A per-width plane pool would
  remove the per-net headers; see the floor above.
* **`test-1364 --native` fan-out** used `getCpuCount()` (32 parallel
  `zig build-exe`). `harness.defaultJobs` on main (uncommitted at this
  branch's base) already sizes it from RAM.
* The compiler is not a SIMD target (AGENTS.md §5); nothing here vectorises.
  The one data-dependent branch removed is the presence test on an SSA map
  read (chunk 0 is the sentinel).

## Suite processes

Strict `-j4` on the rebased branch: 2182/2182, 0 FAIL/XFAIL names (the base
`45022040` also had 0). A sampler polled VmRSS of the runner and all its
descendants every 0.2 s. It ran with a warm `.zig-cache/vera-suite` (203 s
wall), so the child `zig build-exe` mostly hit its cache:

| Class | Peak RSS |
|---|---:|
| `vera-suite` runner | 56.9 MB |
| child `zig build-exe` (warm) | 175 MB |
| sum over live processes | 727 MB |

The `vera` children each live under 0.3 s, so the 0.2 s sampler misses them.
Their per-process peaks are the sweep table above. The ~1 GB single process
seen on main is a cold `zig build-exe` (LLVM) of one testbench. That process is
not VerA's code; fan-out is its only lever (`harness.defaultJobs`). The 16.4 GB
cgroup `memory.peak` is page cache: one strict run writes 17 GB of testbench
artifacts.
