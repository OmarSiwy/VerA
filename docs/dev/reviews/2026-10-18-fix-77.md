# Design review: #77, analog radix width of an integer expression

§10.1: a bug fix runs R6 and R7 (the missing oracle, Principle 19.4).

- **Change**: analog `%h`/`%x`/`%o`/`%b` of an integer expression prints
  the expression's IEEE 1364 width with §17.1.1.3's leading zeros: 32 bits
  for every operator over 32-bit operands and for an unsized literal
  (`ffffffd3`, `000000ff`), all 16 digits for a 64-bit operand. One function,
  `lower/systask.zig` `intSize`, sizes an operand for `%d` (`decimalWidth`,
  #61), the radices and numeric `%s` (`formatOperand`); `formatBits` and
  `decimalSize` are gone.
- **Domain skill(s)**: `compiler-construction`.
- **Hot/cold**: cold. The sizing runs once per display operand at compile
  time; the emitted print runs only at an accepted point.
- **Root cause**: two width rules for one operand. `formatBits` returned
  null for every binary operator and for `?:` arms it could not match, and
  64 for an unsized literal; a null or 64 kept the carrier's minimal digits
  (`cg_display.appendConv` padded only `bits < 64`). `decimalSize` (#61)
  read the same expressions as 32-bit `integer`s, so `%d` and `%h` of one
  operand disagreed.
- **Reading**: IEEE 1364-2005 §5.4.1 Table 5-22 ("Unsized constant number:
  Same as integer"; `i op j`: max(L(i), L(j)); `op i`: L(i); shifts and
  `**`: L(i); `?:`: max(L(j), L(k))), §5.5.1 for the sign, VAMS §3.2 for the
  32-bit `integer`, and VD-116 (every analog integer operation is a 32-bit
  `integer`). §2.6.1/§3.5.1 "at least 32" is VD-124's choice: 32, 64 when
  the value needs more (the rule `frontend/constfold.literalWidth` already
  applies). Fixture 171 asserted 64 bits for `%h` of -42 from §2.6.1 alone;
  Table 5-22 and §3.2 settle it, so its want is now `ffffffd6` and its
  header says why.

## Data (R2)

No table. `$display$width(value, bits)` is now recorded for a radix
operand at any known width, 64 included (was `< 64` only); its range is
unchanged (1..64, `widthRecord` asserts it).

## Containment (R6)

| Module | Error set | Boundary validation | Check budget | Bounds |
| ------ | --------- | ------------------- | ------------ | ------ |
| `analog` `lower/systask.zig` | `Oom` (unchanged) | none new: the operand is already lowered and typed | none | `intSize` recurses on the AST's unary/binary/`?:` operands, as `formatBits` and `decimalSize` did (parser depth bounds it) |
| `device` `cg_display.zig` | `Error` (unchanged) | none: only lowering mints `$display$width` | unchanged asserts | none |

Null from `intSize` means "the carrier does not hold the IEEE bits"; each
caller keeps its pre-#77 answer for it: `%d` an `integer`'s field, a radix
the minimal digits, `%s` E0819. So the `188_numeric_string_*_rejected`
fixtures still refuse (a >32-bit operand under an operator, a signed narrow
`?:` arm against an unsigned wide one, a host-sized parameter).
