# Design review: #81, LLVM segfaults compiling l_utsoi's AMDGCN kernel

- **Change**: after the proof, a second if-conversion pass (`ifconv`
  `.speculate`) turns the remaining branches on solve-dependent conditions
  into selects. These are the arms that hold a domain-restricted op
  (`ln`/`sqrt`/`pow`/integer `/`…) and the arms that run through several
  blocks. Each moved domain-restricted row keeps a guard (`Mir.guard_of`)
  and renders on its domain's safe argument while the guard is false
  (`render.renderSubst`). On NVPTX/AMDGCN a costly select runs both arms
  and the checked math kernels inline (`zSpec`). A host CPU renders the lazy
  arm and keeps the calls.
- **Domain skill(s)**: `compiler-construction`, `gpu-kernel-optimization`,
  `branchless`, `zig`.
- **Hot/cold**: hot. This is the emitted device's `eval` (§11.9). The
  passes themselves are cold compiler passes.
- **Stages run**: R6, R7 (bug fix), R2/R4/R8 for the hot-path change, R10.
  Several are partial; see "Not done" at the end.

## Root cause

LLVM 22.1.8 (what Zig 0.17.0 links; the issue says 21) segfaults in the
greedy register allocator: `SplitEditor::extendPHIKillRanges` ←
`SplitEditor::finish` ← `RAGreedy::splitAroundRegion` ← `doRegionSplit`,
in ESPice's `eval.evalRange__func_0`. That is the whole l_utsoi eval
inlined into one AMDGCN function: 43,215 IR lines, 1,487 phis (725 of
them `<10 x double>` dual vectors), 537 conditional branches. It
reproduces with a standalone `llc -O3 -mtriple=amdgcn-amdhsa
-mcpu=gfx1100 -mattr=+trap-handler` on that one function (26 s, 640 MB).
It is likely llvm/llvm-project#170298 (same function; an asserting build
stops at "SubRange for this mask not found"). The crash is a real LLVM
bug, and how the function is shaped decides whether it fires:

| evalRange__func_0 | crashes | IR lines | phi | vector phi | `br i1` | select |
| ----------------- | ------- | -------- | --- | ---------- | ------- | ------ |
| VerA 7971b23e (ESPice be-139) | yes | 43215 | 1487 | 725 | 537 | 276 |
| main, `zLnD`/`zSqrtD`/`zPowK` made `inline fn` | yes | 43215 | 1487 | 725 | 537 | 276 |
| main as emitted (e7f31ba3's wrappers stay outlined) | no | 45308 | 1503 | 725 | 537 | 276 |

So main compiled only by luck: #59's wrappers happened to stay outlined.
The source of the PHIs is VerA's CFG for an `if` that `ifconv` had to
keep, because an arm held `ln`/`sqrt`/`pow` or another `if` (l_utsoi: 694
data-dependent statement `if`s in the emitted Zig, plus 103 on
`model.su.b` card flags). LLVM cannot if-convert them itself:
`opt simplifycfg<speculate-blocks>` with a folding threshold of 200
removes none of the 537 branches, because the arms call the family's
outlined `log`/`exp`/`pow`.

## The fix

1. `ifconv.Mode.speculate`, run by `lib/root.zig` after the proof. The
   proof read the CFG's dominance evidence, and the verdict (unit float
   modes) is unchanged. On top of `.pure`, the pass (a) follows an arm
   through a chain of single-entry blocks, which is what an inner
   conversion leaves; (b) moves dead phi rows that sit after a
   terminator; (c) moves a domain-restricted row and adds the arm's
   literal (condition, taken) to that row's guard chain, outermost
   first. It never converts a condition the model card alone decides
   (`cardOnly`: the card flags keep their branch, and every evaluation
   takes the same arm). It never converts a diamond whose join phi an
   `.optimized` unit reads (`keepSlice`), where fast-math would turn an
   out-of-domain NaN into poison.
2. Codegen. A guarded row's restricted operand renders as
   `zPick(guard, x, safe)` (`render.renderSubst`): ln/log10/sqrt/pow base/
   divisor take 1, ln1p/asin/acos/atanh/tan take 0, acosh takes 2. These
   are points inside the domain with a finite derivative, so the
   discarded value and its lanes stay finite, and the checked kernel
   (`zLnD`…) reports only where the source ran the op. `eagerSafe`
   accepts a guarded row. In a `.strict` unit a select with costly arms
   on a solve-dependent condition renders
   `(if (comptime zSpec) <both arms, S.sel/zPick> else <lazy arm>)`.
   `zSqrtD`/`zLnD`/`zLn1pD`/`zLog10D`/`zPowK` are
   `callconv(zSpecCc)`, which is `.inline` on a GPU and `.auto` on a host.

| ----- | -------------- | ------------------ | --- | ---------- | ------- | ------ |
| main (luck) | ok | 45308 | 1503 | 725 | 537 | 276 |
| main + inline wrappers | **SIGSEGV** | 43215 | 1487 | 725 | 537 | 276 |
| this change (inline + branch-free, LLVM 22.1.8) | ok | 56692 | 3287 | 660 | 858 | 1594 |

The emitted Zig for l_utsoi goes from 694 data-dependent statement `if`s to
41, with 529 selects behind `comptime zSpec`. That the compile succeeds
does **not** prove the bug is gone: evalRange still has 660 vector phis,
most of them from the 103 kept card-flag branches and from `zPick` on dual
aggregates, and the RA bug is still in LLVM. A prototype that also
converted the card-flag branches got to 60 vector phis. The upstream report
(the reproducer below) is still the real fix.

Reproducer for upstream: `evalRange__func_0` of the crashing build, alone
(`llvm-extract`; 2.8 MB, sha256 8fe02bac…f32c0, 225 KB as `.xz`), with
the `llc` line above. `-O2` also crashes and `-O1` does not.
`llvm-reduce` made no progress in 90 minutes: a register-allocator crash
is lost when almost any part of the function moves. MIR does not
round-trip (`-stop-before=greedy`: the parser refuses wave32's
`implicit $vcc_lo`).

## Goldens and device text that move

- **Every device**: the prelude gains `zSpec`, `zSpecCc` and `zPick`, and
  five checked kernels gain `callconv(zSpecCc)`. On a host this is `.auto`,
  which is what a plain `fn` already is.
- **Every `.strict` select with costly arms on a solve-dependent
  condition**, in any device: its text becomes `(if (comptime zSpec) … else
  <the old lazy text>)`. The host takes the old text.
- **Devices where `.speculate` converts** (point-dependent `if`s with
  `ln`/`sqrt`/`pow`/nested arms, not read by an `.optimized` unit): the MIR
  changes, so the **CPU text changes too**. The `if` statements become
  selects. Arm values used twice become slots computed every evaluation
  (guarded on their safe argument), where before the branch ran them only
  when it was taken. The values should be bitwise the same (the same ops
  on the same operands, with the select picking the arm the branch took),
  but no differential has run and CPU speed has not been measured.

## Not done (out of time, coordinator's call)

The CPU bitwise differential, CPU eval speed (mos1, bsim4va, psp103,
hisimhv, l_utsoi), NVPTX/AMDGCN compile times and frame sizes, the
fixture suite and the golden diff. The coordinator runs one full test
after this commit. If the CPU is slower, the next step is to keep the CFG
on a host. That means rendering a speculated region twice behind `comptime
zSpec`, since the MIR is shared.
