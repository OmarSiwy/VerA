# Design review: #82, the lossy lines on the GPU

- **Change**: a `vera_timepoint` statement that writes a §5.10 held array
  writes it straight into the statement's cache slot in `Instance` when the
  core is handed a mutable `Instance` (`eval`, `evalQ`), and `updateState`'s
  slice stores such an array in its own field (in place, dirty-tracked);
  neither keeps a local copy of the history or returns one through the core
  result. The GPU eval frame of txl and the coupled lines drops from
  165-612 KB to 0.7-25 KB (sparse lanes; 1.5-43 KB dense), and
  `updateState`'s from 84-318 KB to 1.7-24 KB (tables below). CPU output is
  bit-identical, and CPU eval is 1.6-2.3x faster on these models.
- **Domain skill(s)**: `compiler-construction` (codegen), `gpu-kernel-optimization`,
  `gpu-parallel-algorithm-thinking` (part c), `data-oriented-design`,
  `api-design` (the host list).
- **Hot/cold**: hot. The emitted `eval` runs per instance per Newton
  iterate (AGENTS.md §5, §11.9). Evidence: ESPice #139's launch failures
  and ltra_long_run 27 s → 760 s (issue #82).
- **Stages run**: R1, R2, R4, R6, R7, R8, R9, R10 (a hot path, and the
  device text a host links changes; §10.1). No contract table is added, so
  no contract change (`contract.vera_version` names the release, as it does for every change).

CUDA's per-thread stack limit is 262,136 B (ESPice gpu-evaluation.md).

**Attribution.** The frame is two copies of the history, nothing else:
165,264 ≈ 2 × 5 × 16,384 + 1.4 KB; 306,744 ≈ 2 × 9 × 16,384 + 12 KB; and so
on. The models' `(* vera_timepoint *)` statement commits the point accepted
last into the history (`ht[nh] = tacc; ...`), so:

1. every store in the statement went through `zArrW(&a<id>, &p<id>)`, the
   §5.10 copy-on-write, which copies the held array into a local `a<id>`
   (one copy of the history in the frame);
2. the core returned that version by value (`.f62 = p14.*`, the slot's
   `final`) so `zTpStore` could copy it into `Instance.tp<b>_s<k>` (the
   second copy). The held write-back fields (`.f37 = p14.*`) are dead in
   `eval` and LLVM removes them, which is why ltra, whose statement only
   reads the history, has no frame.

Not the derivative lanes: the sparse and dense frames differ by under 2%,
and the residual/Jacobian (`h0`, `h3` dual arrays) is 0.2-14 KB. So the
sparse layout that took mvsg from 432 to 46 KB does not help here; plan
(a) is this storage change, not a layout one.

## The VerA side, landed

**Eval.** In a statement that caches held array `id` (slot `b, k`), a store
writes `zArrWT(T, n, &inst.tp<b>_s<k>, &a<id>, &p<id>)`: with a writable
slot (the core's `inst` is `*Instance`), the first store copies the current
version into the slot and points `p<id>` there; with a `*const` slot it is
`zArrW` on the local, as before. At the statement's join, `zTpFill` points
`p<id>` at the slot, copying the version in when the statement stored none,
so the slot holds the statement's result whichever arm ran, and `zTpStore`
no longer copies the array. The core takes `inst: anytype` in such a device
only, so the `*const Instance` callers (`noisePsd`, `limit`, `collapse`,
...) keep compiling and keep the local copy; only `eval`/`evalQ` (mutable,
`mutable_eval`) write the slot. The cache is still only read on a hit, and
`zTpStore` still marks it valid in the same call, so a slot written by a
miss that does not end in `zTpStore` (`updateState`'s slice) is unreachable.

**updateState.** `state.inPlaceArrays` admits an array a cache re-points
when its slot is in place: the slice stores it in its `Instance` field as
the block runs, and the join copies a hit's cached version into the field
(`zTpHeld`, widening its dirty range to the whole array), so later stores
write the field. The write-back copy and the local both go.

after; ltra's text is byte-identical to before):

## What ESPice changes (not done here; ESPice is not edited)

1. **Re-measure and admit.** Rebuild against this VerA. coupled_ltra,
   coupled_ltra3/4 and txl then launch (frames above); keep them
   host-stepped first (`gpuHostStepped`), which needs no other change.
2. **`gpuRefusal`'s `mutable_eval` rule.** `statusOnlyMutable` refuses any
   `tp0_t` field. A `vera_timepoint` cache is per-instance state the eval
   thread writes in its own resident `Instance`, as the status latch is, so
   it is safe resident: admit it. (It reads by field name; a published
   "what eval writes" table is the §11.8 fix, a VerA follow-up if ESPice
   wants it.) The cache must be dropped wherever the host drops it: the
   device runs `zTpDrop` itself in `updateState`/`stateCtl`/`initState`, and
   a host that rewrites the Instance from the host copy (`pushStepped`)
   uploads the host's dropped `tp0_t` (NaN) with it.
3. **Stop round-tripping the history (plan b), device-stepped.** The
   history is already a device-side buffer: the resident `Instance` rows.
   Run `updateState` and `stateCtl` for these batches on the device (the
   existing `StateKernel`/`CtlKernel`), so an accepted step appends in place
   (ltra's arrays are dirty-tracked, `__dirty`; txl's and the coupled
   lines' are now too) and nothing of the history crosses PCIe. What step
   control reads comes down per step instead: `Instance.bound_step`,
   `discontinuity_order`, the `UpdateResult`, and the device's
   `pendingBreakpoint(inst, t)` (run in the control kernel). That is about
   40 B per instance per step against ltra's 328 KB `Instance` row
   (plus its 328 KB `State`) today.
4. **The convolution (plan c)** is the ltra eval's per-timepoint walk of up
   to 8192 taps in one thread: see below. ESPice's part is a
   warp-per-instance launch of a cooperative eval; VerA's part is the
   reduction lowering. Until both exist, `--backend auto` should keep ltra
   on the CPU: one GPU thread walking the history serially cannot beat a CPU
   core, whatever the transfers cost.
5. **Model option (ESPice's models).** txl.va and coupled_ltra.va commit the
   staged point inside the cached statement so as to label it from the
   next timepoint's step (txlload.c's `trunc((t - h)·1e12)`). Committing it
   in the accepted-point bookkeeping at the end of the block instead would
   leave the statement read-only, so the history would have no `tp` copy at
   all (halving each instance: coupled_ltra4's `Instance` is 2 × 272 KB
   today). It changes the ps label in the rounding case the comment
   describes, so it is a bug-compatibility decision for ESPice.

## Plan (c): a warp-parallel convolution, designed, not built

ltra's rebuild (ltra.va's "fused walk newest -> oldest") is, per tap i, a
coefficient from the kernel's twice-integrated value at `t - ht[i-1]` and
`t - ht[i]`, times `hv[i] - v0`, summed. Written as a recurrence it carries
`h1hiv1`, `h2hiv1`, ... from tap to tap and stops early on `chopreltol`, so
it is serial as written; but every carried value is a pure function of
`t - ht[i]`, so the walk is a map over i (each tap computes its two kernel
values, 2× the transcendental work) and a sum: span O(log n) instead of
O(n). The early stop becomes a mask (`chopreltol = 0`, the default, never
stops).

Three pieces, in order:

1. **Model (ESPice):** rewrite the walk as an independent-term sum.
2. **VerA:** a reduction loop form (an attribute on a `for` whose only
   loop-carried values are `+` accumulators, refused by clause otherwise)
   and a contract group parameter on `eval`: a comptime `G` with `lane`,
   `width` and `sum`. The loop runs `i = lo + G.lane; i < hi; i += G.width`
   and each accumulator ends `G.sum(acc)`. On the CPU `G` is width 1 and
   `sum` the identity, so the device text compiles to today's loop (an R8
   probe must show IDENTICAL), and CPU output stays bit-identical. On a GPU
   the sum order differs from the CPU's, so results agree to rounding,
   within a deck's tolerance, not bitwise.
3. **ESPice:** launch such a device's eval one warp per instance (32 lanes
   share the instance; everything outside the loop runs uniformly; lane 0
   stamps), with `G` the warp (shuffle reduction).

Not built here: it changes the eval ABI (a new comptime parameter every
host passes, a contract change, shipped in a VerA release (`vera_version`)), needs the model rewrite first, and is
not verifiable without the ESPice launch. The device-resident history
(item 3 above) is the precondition: with the 328 KB row still pushed every
step, a parallel walk would only move the bottleneck.

## Why no history-buffer table (yet)

A published table (each held array's `Instance` offset, length, element
and dirty-range offset) would let a host-stepped batch upload only the
dirty slice of each history. Device-stepping (item 3) makes the transfer
disappear instead of shrinking it, and needs no new contract surface: the
device-resident `Instance` already is the buffer, and the in-place appends
and dirty ranges already exist. A runtime-sized buffer ("sized at
prepare", lifting the 8192/2048 `cap` ceilings) is a layout change (history
outside `Instance`, a contract change, shipped in a VerA release (`vera_version`)) whose motive is capacity, not
#82's speed; it is recorded here and not built.

## Seams (R4)

One axis: whether the core's `inst` is writable, decided at comptime by
the caller (`eval`/`evalQ` hand `*Instance`, every other entry point
`*const`). Rung 5 (a comptime generic over the pointer type: `inst:
anytype`, `zArrWT`/`zTpFill` branch on `pointer.attrs.const`). The rung
below (one concrete signature) fails: a `*Instance` core cannot be called
from the `*const Instance` contract entry points, and a `*const` one cannot
write the slot. Only devices with an in-place slot get `anytype`; every
other device's text is unchanged. Probe: the PTX table (the mutable
instantiation has no local copy) and the CPU differential below (both
instantiations compute the same bits).
