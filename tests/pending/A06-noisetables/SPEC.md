# A06 — `noise_table` / `noise_table_log` reach the output spectrum

VerA compiles §4.6.4.3/§4.6.4.4 tabulated noise and exports it. ARPice ignores
the export. The measured output noise of a circuit whose only generator is a
tabulated one is therefore **identically zero at every frequency**, instead of
the interpolated table.

## The defect, both halves, reproduced

**VerA half — the table IS emitted, correctly.** `espice` compiled
`a06_ntab.assets/a06_ntab_lin.va` and the generated device carries
(`ARPice/.zig-cache/espice-hdl/712bf75e…/device.zig:469`):

```zig
pub const noise_tables = [_]contract.NoiseTable{
    .{ .interp = .linear, .points = &.{ .{ 1000.0, 1e-18 }, .{ 5000.0, 9e-18 }, .{ 9000.0, 4e-18 } } },
};
pub const noise_gens = [_]contract.NoiseGen(Self){
    .{ .row = @intFromEnum(U.p), .col = @intFromEnum(U.n), .kind = .table, .source = 0, .table = 0 },
};
pub fn noisePsd(…) [noise_gens.len]contract.PsdTerm {
    return .{
        .{ .white = 0 }, // noise_tables[0]
    };
}
```

`a06_ntab_log.va` likewise emits `.interp = .log` with the two knots. Sorting,
`.interp` selection and the `.table = 0` back-reference are all right.

**ARPice half — nothing reads it.**

```
$ grep -rn noise_tables ARPice/src ARPice/include     # zero hits
```

The whole noise path stops at the parametric triple:

| file:line | what is missing |
| --- | --- |
| `ARPice/src/problem/device_ir.zig:79-85` | `NoiseSource` has `white`/`flicker`/`ef` and **no table field** — the transport has nowhere to put a tabulated PSD. |

| `ARPice/src/analysis/pss/pnoise.zig:41` | second, independent copy of the same formula — the `.pnoise` sideband PSD. Fixing only `ac/noise.zig` leaves `.pnoise` silently zero. |

## LRM clauses covered

**§4.6.4.3 `noise_table`** (`docs/ch4-expressions.html`):

> "The noise_table() function interpolates a set of values to model a process
> where the spectral density of the noise varies as a piecewise linear function
> of frequency."

> "noise_table() performs piecewise linear interpolation to compute the power
> spectral density generated by the function at each frequency between the
> lowest and highest frequency in the set of values. For frequencies lower than
> the lowest frequency in the value set, noise_table() returns the power
> specified for the lowest frequency, and for frequencies higher than the
> highest frequency, noise_table() returns the power specified for the highest
> frequency."

**§4.6.4.4 `noise_table_log`**:

> "The difference is that noise_table_log() interpolates logarithmically. For a
> frequency f not specified in the input data, the noise power shall be computed
> using the two pairs (f1,p1) and (f2,p2) in the input … where f1 is the largest
> frequency value in the input data less than f and f2 is the smallest frequency
> larger than f (that is, f1 < f < f2); the noise power P is computed as:
> `P = pow(10, log(p1) + (log(p2)-log(p1)) * (log(f)-log(f1)) / (log(f2)-log(f1)))`"

> "As with noise_table(), for frequencies lower than the lowest frequency in the
> value set, noise_table_log() returns the power specified for the lowest
> frequency, and for frequencies higher than the highest frequency,
> noise_table_log() returns the power specified for the highest frequency."

Figure 4-14 is the discriminating picture: the same knots give *bowed* segments
under `noise_table` and a *straight line* under `noise_table_log` on a log-log
plot.

## The circuit, and why every expected number is exact

Identical in all four decks:

```
Vin in 0 DC 0 AC 1
Ns in out a06_noiseless_res     ; VA 1 kOhm, declares NO noise generator
Nt out 0  a06_ntab_{lin,log}    ; VA 1 kOhm + the tabulated current source
```

* A SPICE `R` would inject `4kT/R`, dragging kB and T into every expectation.
  Both resistors are Verilog-A devices with no noise call, so ARPice's
  `collect_noise` hook is null for them (`eval.zig:1305`) and **the tabulated
  source is the only generator in the circuit**.
* `Vin` is a short in the small-signal problem, so the impedance seen at `out`
  by the generator on branch `(out, 0)` is `1000 ∥ 1000 = 500 Ω`, purely real
  and flat — the deck has no reactance.
* Therefore `S_V(f) = 500² · S_I(f)` and the reported column is
  **`onoise_spectrum(f) = 500 · sqrt(S_I(f))` V/√Hz**.

That gain is not assumed. Replacing the tabulated device with
`white_noise(4.0e-18)` — same magnitude as the upper clamp — and running the
same deck on the current build gives `onoise_spectrum = 1.0e-06` at both
frequencies, exactly `500·sqrt(4e-18)`, and `inoise_spectrum = 2.0e-06`,
exactly `onoise/0.5` for the 0.5 divider gain. So the transfer half of every
oracle below is already validated against the live simulator; only the PSD half
is under test.

### Linear table (`a06_ntab_lin.va`)

| f [Hz] | 1000 | 5000 | 9000 |
| --- | --- | --- | --- |
| S_I [A²/Hz] | 1.0e-18 | 9.0e-18 | 4.0e-18 |

Knots are non-monotone on purpose: segment 1 rises, segment 2 falls. Powers are
`{1,9,4}·1e-18` so the square roots are `{1,3,2}·1e-9` exactly.

### Log table (`a06_ntab_log.va`)

| f [Hz] | 1.0e3 | 1.0e6 |
| --- | --- | --- |
| S_I [A²/Hz] | 1.0e-18 | 1.0e-24 |

log-log slope `= log10(1e-24/1e-18) / log10(1e6/1e3) = -6/3 = -2`, so the
clause's formula closes to `S_I(f) = 1e-18 · (f/1000)^-2` on `[1e3, 1e6]`.

## One line per fixture

**`a06_ntab_lin_interior.sp`** — §4.6.4.3, `.noise … lin 9 1000 9000`, nine
rows. Pins three *tabulated* points and six *interior* points:

| f | derivation of S_I | S_I [A²/Hz] | expected `onoise_spectrum` [V/√Hz] |
| --- | --- | --- | --- |
| 1000 | table row, verbatim | 1.0e-18 | 5.0e-07 |
| 2000 | `1e-18 + 2e-21·1000` (slope `(9e-18−1e-18)/4000 = 2e-21`/Hz) | 3.0e-18 | 8.660254037844387e-07 |
| 3000 | `1e-18 + 2e-21·2000` | 5.0e-18 | 1.118033988749895e-06 |
| 4000 | `1e-18 + 2e-21·3000` | 7.0e-18 | 1.3228756555322954e-06 |
| 5000 | table row, verbatim | 9.0e-18 | 1.5e-06 |
| 6000 | `9e-18 − 1.25e-21·1000` (slope `(4e-18−9e-18)/4000 = −1.25e-21`/Hz) | 7.75e-18 | 1.3919410907075056e-06 |
| 7000 | `9e-18 − 1.25e-21·2000` | 6.5e-18 | 1.2747548783981962e-06 |
| 8000 | `9e-18 − 1.25e-21·3000` | 5.25e-18 | 1.14564392373896e-06 |
| 9000 | table row, verbatim | 4.0e-18 | 1.0e-06 |

**`a06_ntab_lin_clamp.sp`** — §4.6.4.3 clamping, `.noise … lin 2 10 90000`.
`f = 10 < 1000` holds the lowest row: `S_I = 1.0e-18`, `onoise = 5.0e-07`.
`f = 90000 > 9000` holds the highest row: `S_I = 4.0e-18`, `onoise = 1.0e-06`.
The two clamps differ, so returning the wrong endpoint fails; extrapolating the
final `−1.25e-21`/Hz slope to 90 kHz would give a *negative* power, which is not
a PSD at all.

**`a06_ntab_log_interior.sp`** — §4.6.4.4 interpolation, `.noise … lin 3 1000 3000`.

| f | derivation of S_I | S_I [A²/Hz] | expected `onoise_spectrum` [V/√Hz] |
| --- | --- | --- | --- |
| 1000 | first table row (formula degenerates to p1) | 1.0e-18 | 5.0e-07 |
| 2000 | `1e-18·(2)^-2 = 1e-18/4` | 2.5e-19 | 2.5e-07 |
| 3000 | `1e-18·(3)^-2 = 1e-18/9` | 1.1111111111111111e-19 | 1.6666666666666667e-07 |

Discrimination: §4.6.4.3's *linear* rule on the same two knots would read
`1e-18 + (1e-24−1e-18)·1000/999000 = 9.98999e-19` at 2000 Hz, i.e.
`onoise = 4.9975e-07` — a factor of ~2 away. This fixture fails a host that
implements one clause and reuses it for the other, which is precisely what
Figure 4-14 warns about.

**`a06_ntab_log_clamp.sp`** — §4.6.4.4 clamping, `.noise … lin 2 500 2000000`.
`f = 500 < 1000` holds the lowest row: `S_I = 1.0e-18`, `onoise = 5.0e-07`
(extrapolating the `-2` slope would give `4e-18` / `1.0e-06`, exactly 2× wrong).
`f = 2e6 > 1e6` holds the highest row: `S_I = 1.0e-24`, `onoise = 5.0e-10`
(extrapolation would give `2.5e-25` / `2.5e-10`). The upper clamp doubles as the
pin on the top tabulated power, which is returned verbatim.

Four positive fixtures, zero reject fixtures.

## Deliberately NOT covered here

* **File-input tables** (§4.6.4.3 `noise_table("file.tbl")`, `#` comments,
  whitespace-separated pairs). VerA already pins the compile side in
  `tests/fixtures/ch04_expressions/lrm_4_6_4_3.va`; nothing about the host's
  interpolation changes with the input syntax.
* **Unsorted input.** `tests/fixtures/ch04_expressions/181_noise_table_topology.va`
  pins that VerA sorts, and the emitted `noise_tables` above confirms it. The
  host is contractually handed ascending points.
* **Integrated noise.** The `Integrated Noise` plot is omitted from all four
  oracles: ngspice's per-source log-log band fit (`ninteg.c:27-45`, ported at
  `ac/noise.zig:27-39`) is a separate algorithm, and pinning it here would
  couple this row's numbers to it. Add once the spectra are correct.
* **`inoise_spectrum`.** Would only re-pin the 0.5 divider gain already
  validated above.
* **`.pnoise` and `.tran_noise`.** Both read the same `NoiseSource` and are
  equally blind (`pnoise.zig:41` has its own copy of the parametric formula),
  but a PSS/transient oracle needs its own hand-derivation. Named in the table
  above so the fix is not scoped to `ac/noise.zig` alone.
* **§4.6.4.6 correlated tabulated sources** — `NoiseSource` has no partner field
  at all yet (`eval.zig:1709-1711`), a strictly larger gap.
* **The optional `name` argument** as a noise-contribution label in the report;
  ARPice has no per-source contribution summary.

## How to run these

Today, by hand, from this directory (all four already run and all four already
report the wrong answer):

```
zig build -Doptimize=ReleaseFast --prefix zig-out       # in ARPice
/…/ARPice/zig-out/bin/espice a06_ntab_lin_interior.sp -r /tmp/a06.raw
```

Wired up — `ARPice/tests/fixture_catalog.zig:6-21` walks `tests/fixtures`
recursively, so no `build.zig` edit is needed:

```
cp -r /…/VerA/tests/pending/A06-noisetables/a06_ntab.assets \
      /…/VerA/tests/pending/A06-noisetables/a06_ntab_*.{sp,expected.json} \
      /…/ARPice/tests/fixtures/noise/
cd /…/ARPice && zig build test -- --filter a06_ntab
```

The `netlist_sha256` in each oracle is the SHA-256 of its own `.sp` and is
checked at `tests/test_correctness.zig:156`; re-hash after any edit to a deck.
